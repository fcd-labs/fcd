## The experiment

Are one intent and one description of a sub-product together enough for an AI squad to build the sub-product?

The answer: yes, provided the harness is in place. Read further down [how FCD-demo was made](#how-fcd-demo-was-made): by a product owner, Claude in the chat and two AI squads.

## The intent: Ordering

1. **Persona and user story:** as a guest I want to choose from a menu, so that I can pass my order to the kitchen, bar and till, so that I get my order.
2. **Why (objective):** the guest can order.
3. **Measure (key result):** every order from the guest arrives at kitchen, bar and till.
4. **Behaviour as scenarios:**
   - Given a menu, when the guest chooses, then the order goes to kitchen, bar and till.
   - Given a placed order, then the guest sees that the order was sent to kitchen, bar and till.

Why and measure are separate: the why is the direction and changes little; the measure you adjust after what you learn. What is not described is out of scope.

## The sub-product: Ordering

1. **Responsibility.** Does: show the menu, let the guest choose, and send the order to kitchen, bar and till. Does not: manage the menu, or payment. The menu is a fixed, declarative file in the repository; changing the menu goes through the pipeline.
2. **Users:** the guest.
3. **Interfaces:** Ordering sends one order, the whole order, directly to kitchen, bar and till, according to a contract (contract first): [order.openapi.yaml](https://github.com/fcd-labs/sk-bestellen/blob/main/contracts/order.openapi.yaml). Frontend and backend also talk via a contract. The contracts are in git, with their own version, and in an API registry (Apicurio Registry).
4. **Intents:** Ordering.

In this version kitchen, bar and till exist as stubs: separate containers, not part of the sub-product. The intent is not the sub-product: which sub-product fulfils an intent is an architecture choice.

## The pipeline

One bash script is the only way to build, test, check, deploy and release. The Pipeline runs locally, only takes what has been merged from a local git server, and deploys with docker-compose. It starts with the button on the Dashboard: the approval by the product owner.

| Block | Steps | Quality gate |
|---|---|---|
| Build, per container | 1. Static check, 2. Unit tests, 3. Contract test | Code gate |
| | 4. Build | |
| Build, the sub-product | 5. Integration tests | Build gate |
| | 6. Security and freshness, 7. SBOM and licences | Security gate |
| Deploy | 8. Deploy, 9. End-to-end tests | Deploy gate |
| Release | 10. Release: a tag and the changelog | Approval, before releasing |

If a gate closes, the pipeline stops: nothing is deployed or released. The pipeline is deliberately incomplete: ESLint, test coverage, the consumer contract test, DAST and performance tests are on the picture and the Dashboard as backlog. Grow through doing.

## Learning

The Dashboard closes the circle. It shows the key result from the intent: does every order reach kitchen, bar and till (the stubs)? It also shows the pipeline live, per step and per gate, the new version and the changelog.

## The demo

Ordering 1.0.0 has a deliberate bug: an order does not reach the bar. The key result is red. The patch 1.0.1 is ready. The product owner starts the pipeline, you watch the steps and gates live, and then the order does reach the bar: the key result is green. Measure, learn, fix.

## Deviations for the demo

All steps and gates stay. To keep the pipeline within 5 minutes, five steps are shortened for the demo only, with approved deviations: the images are pre-warmed, the security, freshness and licence scan comes from the cache, end-to-end runs only the core path "place an order", and releasing is a local tag without a GitHub Release. Nothing is pushed to remote during the demo. Everything runs locally, in one environment, with docker-compose instead of Kubernetes.

## How FCD-demo was made

FCD-demo was made by a product owner, Claude in the chat and two AI squads. The answer to the experiment: one intent and one sub-product description are enough, provided the harness is in place.

### Knowledge in the model

AI did not invent FCD. The FCD model bundles professional knowledge of quality, testing, audit, releasing and continuous delivery: the principles, the quality gates, comply or explain, one source. That knowledge forms the harness: the principles of FCD-demo, on the [Full Circle Delivery picture](#the-full-circle-delivery-picture) above. AI helped to work out the model and to build the showcase.

### One intent

It started with one sentence, [the intent Ordering](#the-intent-ordering): as a guest I want to choose from a menu, so that my order reaches kitchen, bar and till. And with one question: is one intent, with a description of the sub-product, enough for an AI squad?

### Two tracks at once

The model and the showcase grew in parallel. The model gave the showcase direction; the showcase showed where the model did not fit yet. The model grew first in conversations in the chat; the showcase followed in nine days.

### The roles

| Role | Who | What |
|---|---|---|
| Product owner | sim007 | The what and why, the decisions, the Approval |
| Thinking partner | Claude in the chat | The model, the FCD language, the site and the pictures; the assignments for Claude Code |
| AI squad | Claude Code | sk-bestellen: the sub-product Ordering; first a proposal, then push |
| AI platform squad | Claude Code | The platform, the Pipeline and the Dashboard; first a proposal, then push |

### A circle too

An intent became an assignment in the chat. Claude Code made a plan, the product owner chose, and Claude Code built, tested and reported back. With that report the site was updated. What was learned became the next intent.

### What chafed, and what it brought

- **The site lagged behind the showcase.** That led to one source: the configuration lives in fcd and goes to the showcase, not the other way round.
- **Words matter.** The process picture became the Full Circle Delivery picture, process became delivery, and the FCD language got a name.
- **The AI found a contradiction in the principles:** a deviation on a principle where explain was not allowed. Now the generator checks this itself.
- **The harness is not finished.** What is missing is backlog: a choice, not a gap.

### The answer

Yes, provided the harness is in place. What the AI squads made went through the same steps and quality gates, within the principles, and the decisions stayed with the product owner. AI needs delivery. Delivery needs AI.
